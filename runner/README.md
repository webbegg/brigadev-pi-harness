# brigadev-runner

A headless, durable ticket runner for the brigadev workflow. It takes a feature doc whose `## Tasks` list the user approved and runs the tickets one at a time, each in a fresh worker conversation, on [`@earendil-works/pi-durable`](https://www.npmjs.com/package/@earendil-works/pi-durable). State lives in storage (SQLite by default), so killing the process and starting it again resumes at the last checkpoint instead of redoing finished tickets.

This package is a separate, private package: the Pi extension in the repo root does not depend on it. It reuses the Pi-free modules in `../lib/` (`ticket-list.ts`, `agents.ts`, and the guard, evidence, and check modules listed under [The worker obeys the guard](#the-worker-obeys-the-guard)) by relative import.

## Status: experimental

- `pi-durable` is itself marked experimental and its API changes without notice, so the four `@earendil-works/*` dependencies are pinned to exactly `1.6.0` (Pi 1.5.2 ships pi-ai 1.5.2, which is why this is not part of the root package).
- Prototype scope (`tasks/durable-runner.md`): the ticket loop (T3), its guard, check tool, and commit gate (T4), and the human gates as durable signals: ticket decisions, command approvals, pause and resume, and the `status`/`answer`/`pause`/`resume` commands (T5). The PR → CI → merge loop with its merge-approval signal (T6, see [The PR loop](#the-pr-loop-s2b-s3-s4)). The board that shows the loop and takes your answers in a browser (T7, see [The board](#the-board-s6)). A dollar cost cap per loop (see [The cost cap](#the-cost-cap-s1)). Not there yet: parallel tickets, releases. The **worker** never pushes, merges, or publishes (its guard blocks them); the **runner** does, in deterministic code, only in the PR loop. The agent runs with the user's credentials taken out of its environment and its work is checked before it is trusted: see [Containment](#containment-what-it-stops-and-what-it-cannot); read what it cannot stop before running this unattended on a machine that holds credentials.

## Run

The runner starts only in its own **linked git worktree, on a feature branch** (Q5): it never shares a checkout or a branch with a live Pi session, and never commits on the default branch. Create one from your repo:

```sh
git worktree add ../<repo>-runner -b <branch>
```

`start` refuses (exit 1, after the doc check, before any model call) when the current directory is not a git repository, is not a linked worktree (its git dir equals the common dir), is on a detached HEAD, or is on the default or a protected branch (`main`, `master`, the `origin/HEAD` target, per `lib/commit-branch.ts`; also when the default branch cannot be determined). `BRIGADEV_RUNNER_UNGUARDED` no longer exists: the guard is always on.

```sh
export ANTHROPIC_API_KEY=...
# optional: BRIGADEV_RUNNER_MODEL (default claude-sonnet-5-5)
cd ../<repo>-runner
node --disable-sigusr1 <path-to>/runner/src/cli.ts start ~/.brigadev/<repo>/tasks/<feature>.md            # tickets, then the PR loop
node --disable-sigusr1 <path-to>/runner/src/cli.ts start ~/.brigadev/<repo>/tasks/<feature>.md --no-pr    # tickets only
```

State is stored in `<brigadev home>/<repo>/runner.sqlite` (`~/.brigadev/<repo>/` unless `BRIGADEV_HOME` is set; `<repo>` is the main checkout's folder name, shared by every worktree, like the feature documents and the evidence). Running `start` again for the same doc finds the same loop task and continues it. What the loop was started with is fixed: `start` with the other `--no-pr` choice, or from another worktree than the loop's, exits 1 and says how the loop was started (it would otherwise push and open a PR after `--no-pr`, or run the guard in a checkout the commits are not in). Exit codes: 0 every ticket done (and, with the PR loop, the PR merged), 1 refused, failed, stalled, or parked (waiting for a decision, a resume, or the merge approval), 2 usage.

## Commands

```sh
brigadev-runner start  <feature-doc> [--no-pr] [--cap <dollars>] [--web [--port N]]  # run the loop (and the PR loop); returns when it ends or parks on a person (--web: serve the board, stay up)
brigadev-runner status <feature-doc>                              # read-only
brigadev-runner answer <feature-doc> <T#> <1..n|text> [--approve]  # answer a parked decision
brigadev-runner pause  <feature-doc>                              # pause at the next pick
brigadev-runner resume <feature-doc> [--cap <dollars>]            # lift a pause, or a PR loop stop (needs-you); a stop at the cost cap needs --cap
brigadev-runner merge  <feature-doc>                              # approve the merge of the PR the PR loop opened
```

- `status` prints the loop state (`running`, `sleeping`, `paused: <reason>`, `done`, `stalled`, `failed`), every ticket's status from the doc, and each open decision with its numbered options, the `(recommended)` mark, the deadline, and the exact `brigadev-runner answer <doc> <T#> <1..n|text>` command. It opens the store read-only: nothing is recovered, written, or scheduled, and it creates nothing for a doc that was never started.
- `answer`: the choice is an option number or free text (several words need no quotes). A number outside the options is `invalid` (exit 2) with the reason. `--approve` approves the decision's `command` whatever the option labels say.
- Signal results map to output and exit codes: `delivered` 0; `duplicate` and `closed` are final answers, printed as such, 1 (a second answer, or an answer after the deadline or after the loop ended); `invalid` 2 with the reason; `not_found` 1 (no such loop, or no decision for that ticket). `pause` while paused and `resume` while not paused are refused (1): a stale `resume` would otherwise lift the next pause.
- `merge` delivers the merge approval to the PR loop (see below); like `answer`, it needs no API key, runs nothing, refuses while a `start` holds the store, and maps `duplicate`/`closed`/`not_found` to final answers (exit 1). It is refused (exit 1) unless the PR loop is waiting for the approval, and says where it is instead.
- `answer`, `pause`, `resume`, and `merge` check the doc like `start` does (it must be readable and valid), but not the worktree rule: they touch no checkout. They need no API key and never run a worker.

### One process per store (the multi-process limitation)

pi-durable allows one writer per storage. Checked on pi-durable 1.6.0: a second Harness opened on the SQLite file while another process runs a ticket marks that ticket task `pending` with `restarts + 1` (open recovers `running` tasks), and a running Harness does not see a signal another process committed (a `pause` delivered that way was ignored and both tickets still ran). So:

- `answer`, `pause`, and `resume` open a **short-lived Harness that delivers one signal in one commit and closes**, before anything is scheduled (`Harness.signal()` and `wait()` start the scheduler; the runner's `deliver()` commits `tx.signal()` instead). A signal delivered early is kept by the task and consumed the next time the loop looks.
- `start` takes `runner.sqlite.lock` and refuses a second `start`. The lock is an OS lock that dies with its process, not a file: `<store>.lock` is an SQLite database held in one `BEGIN EXCLUSIVE` transaction (`locking_mode=EXCLUSIVE`, `busy_timeout=0`) until `start` ends, so there is no stale lock to take over and two racing processes cannot both hold it. The holder's pid is written to `<store>.lock.pid` after the lock is taken, for the messages only (`another process` while it is not written yet). `answer`, `pause`, and `resume` refuse (exit 1) while it is held; `status` reads regardless.
- `start` therefore does **not** wait in the foreground for an answer it could not see: when the loop is asleep on a decision or a pause and nothing can run, it prints where it waits and the commands to use, and exits 1. Answer, then run `start` again; the loop continues from storage (an answer is read at the loop's next pick).
- Consequence: a user `pause` reaches a loop only through the store, so it takes effect at the first pick after the next `start` (or, in a process that holds the Harness itself, as in the tests, at the next pick of the running loop). There is no remote pause of a running `start` through the CLI: with `start --web` the board is the remote, because it delivers inside the process that holds the store (see [The board](#the-board-s6)). The refusal that `answer`, `pause`, `resume`, and `merge` print while a `start` holds the store says so.

## What the doc must look like

`start` refuses the doc, listing every error, unless it passes `validateForRun` (S7: each unfinished ticket has `done:`, known `deps:`, no cycles) and the runner-only rules:

- `T3 done: is not a command`: the runner can only run commands, so an unfinished ticket's `done:` must be a backticked command.
- the doc has a `## Log` section (every finished ticket appends one line).

## How it works

- `brigadev.ticket-loop`: `pick` (first ready ticket in doc order) → `launch` (mark it `in_progress`, create the child) → `record` (write `done` or `blocked` and one `## Log` line) → `pick`. A ticket that fails its attempts is `blocked` with `needs you: <reason>`; tickets that depend on it wait and independent ones continue. Two failed tickets in a row **pause** the loop (below). It ends `done` when every ticket is done or dropped, and `stalled` when only blocked or dependent tickets remain and no decision is open.
- `brigadev.ticket`: per attempt, a worker conversation owned by the task (instructions from `assets/agents/brigadev-worker.md` plus the ticket and, on a retry, the failure output). Before the done command (and before anything the worker made is trusted) the runner checks the worker left alone what it must not (see [Containment](#containment-what-it-stops-and-what-it-cannot): the feature document, `brigadev.json`, git's config and hooks, every branch and tag, the remote's refs); a change parks the loop. Then the done command runs in the repo, with the contained environment, in its own process group, with a timeout (30 minutes; settings `runner.doneTimeoutMinutes` overrides; the whole group is killed on the timeout or an abort) and its output kept to the last 1 MB: it passes when it exits 0 **and** HEAD moved since the ticket started (the worker must have committed). Up to 3 attempts.
- The doc is written only after re-reading it. A user edit to the running ticket's line or a finished one's pauses the loop (`doc edited: T#`) and nothing is overwritten; edits to pending tickets are picked up at the next pick; a changed spec reopens its linked done tickets (`reopened: S# changed`). Writes are atomic (temp file + rename). One exception to "picked up at the next pick": a change of the doc **while a worker conversation runs** parks the loop (`the worker changed the feature document; check them, then resume`), because the runner cannot tell it from a write by the worker (a worker that adds a ticket whose `done:` is a shell command). An edit between conversations, as before, is yours.

## The cost cap (S1)

One dollar cap per loop (a doc's `start`: its tickets, their attempts, the PR loop's verify and its `FIX-n` tickets), **$5 unless `start <doc> --cap <dollars>` says otherwise** (a positive number; `--cap 0`, `--cap -1`, `--cap abc`, or `--cap` without a value is a usage error, exit 2). The cap is stored durably with the loop (a Session document keyed by the loop task, `src/cost.ts`), so a reopen keeps it; a later `start` of the same doc without `--cap` keeps the stored cap, and with `--cap` changes it and says so on stdout (`cost cap changed: $5.00 → $10.00 (spent $1.23)`). The new cap is read at the next boundary, not by a conversation that is already running.

**What counts.** The sum of `usage.cost.total` in pi-durable's `pi.usage` (the `models` and `tools` buckets) over every conversation the loop owns, directly or through its descendant tasks: every ticket attempt's worker conversation, the verify conversations, the fix tickets' conversations. Failed and aborted attempts count. Every place that creates such a conversation lists it in the loop's ledger in the same commit, so the spend is read from that list (a finished conversation's total is remembered, only the newest is read again) and no other loop's conversation is ever read. **Usage a provider does not report is not counted**: the runner can only add what `pi.usage` holds (the faux provider reports none, so the tests price every response themselves).

**Where it is checked.** Before new spend: before each ticket's first attempt (the loop), before each further attempt (the ticket task), before the verify conversation, and before each `FIX-n` ticket (the PR loop). At or over the cap the loop **parks needs-you** with `cost cap reached: $5.12 of $5.00 spent`, the same way the other parks work: the ticket loop pauses on a `brigadev.resume` wait (`status` shows `loop: paused: cost cap reached: ...`; a ticket that was between attempts stays `in_progress` with the reason as its note), or the PR loop stops (`pr: needs-you`, one PR comment when a PR exists, one Log line). The board shows the same in its Needs you column.

**Inside a running conversation.** Once the loop's spend is at or over the cap, the guard's `beforeTool` hook blocks every further tool call of that conversation with `Blocked: the loop's cost cap ($5.00) is reached; finish now.`, so the run ends quickly. The hook is cheap (it reads two documents of its own conversation: the cap and the spend before it started, which is exact because a loop runs one conversation at a time, and its own `pi.usage`) and fails safe: spend that cannot be read does not block, and is logged to stderr. The verdict tool of a verify run is the one call let through, because it is how that run finishes.

**The overshoot bound.** The cap is checked between responses, never inside one: the run in progress can exceed it by the responses it makes before its tools are blocked and it answers (the response that reached the cap, the model's reply to the blocked calls, and the final answer), and a ticket's done check is not a model cost. Nothing else is spent: the next boundary parks.

**Continue.** `brigadev-runner resume <doc> --cap <dollars>` (or the board's cost-cap prompt: `+$5`, `+$10`, or an amount) writes the new cap and delivers the resume **in one commit**. The new cap must be **above the current spend**, else it is refused (exit 2 on the CLI, 409 on the board) and nothing is delivered; a plain `resume` at a cost-cap park is refused (exit 2) with the hint to pass `--cap`, unless the stored cap is already above the spend (raised by `start --cap`), and `--cap` at any other pause is refused too. A ticket that parked between attempts runs again from the commit it started at with a fresh attempt count; the PR loop continues at the phase that stopped, with a fresh fix budget.

`status` prints `spend $1.23 of $5.00` (also for a loop that ended), and the board shows it in the phase detail, with each ticket card's own spend.

## Decisions, approvals, pause and resume (S4, S9)

The human gates are pi-durable signals on the loop task, answered from the CLI after any restart. The signal kinds and key helpers are in `src/signals.ts`; T6's merge approval reuses `deliver`, `signalExit`, and `signalLine` with a kind of its own.

**Decisions.** The worker has a runner tool `ask_user_choice` (`src/decision.ts`) with the Pi tool's parameters: `question`, `options` (`{label, description?}`, 2–6), `recommended` (1-based), plus `command`: an exact bash command the worker needs approved. The worker never picks a product or design option; it asks. Calling the tool ends the attempt without a failure: the tool writes the question to a conversation document (`brigadev.decision`) in its own commit and returns `control: { terminate: true }`, which ends the run with no further model request; the ticket's `check` phase reads that document instead of running the done check, and the ticket task completes with `{ decision, attempts }` where `attempts` counts only the attempts before it. (A task can read only its own conversation's history, so a document is how the tool hands the question to the ticket task.) An invalid call (not 2–6 options, bad `recommended`) is an error result the worker sees; nothing parks.

The loop then records the ticket line as `— blocked needs you: decision: <question> (answer: brigadev-runner answer <doc> <T#> <1..n|text>)` (the doc path and ticket filled in) and one `## Log` line, and continues with independent ready tickets; tickets that depend on it wait. When nothing is ready and a decision is open, the loop sleeps on the `brigadev.answer` signal of every open decision, key `decision-<T#>-<round>` (`decision-T1-1`, then `decision-T1-2` for that ticket's next question; a key serves one wait and is never reused), with the earliest deadline. Each question's deadline is 24 h after it was asked and is memoized once. On a wake:

- answered: the ticket goes back to `in_progress` and reruns with a fresh attempt count; its brief has a `## Decision from the user` section (question, numbered options, the answer);
- expired: the line becomes `— blocked needs you: no answer within 24 h` (and a Log line), and the answer key is closed (a late `answer` is `closed`). One sleep has one deadline and expiry marks every unanswered key of that sleep, so when an earlier question expires the others get a new key (`decision-T3-2`) with their own deadline unchanged;
- the user hand-edited the parked line off `blocked` (e.g. back to `pending`) meanwhile: at the next pick it is theirs again, picked as usual, and its decision is dropped. (A sleeping loop is not woken by a doc edit; it reads the doc at its next pick, which an answer, a deadline, or a ticket finishing triggers.)

**Command approval.** The guard still denies confirm-class commands mid-run as `needs you: …` (Q6: nothing parks inside a tool call). The denial now tells the worker: if the ticket cannot be done without the command, call `ask_user_choice` with `command` set to the exact command and an option whose label starts with `Approve`. The rule for what approves it, kept simple: the decision has a `command`, and the answer is `--approve`, or the answer is an option whose label starts with `Approve` (by its number, or by typing the label exactly). Any other answer lifts nothing. When approved, the rerun's **first attempt's** worker conversation is created with a `brigadev.approval` document holding the command, and the guard lifts the permission policy's confirmation for a bash call whose command string is **identical** to it, **once**: the guard counts the conversation's earlier calls of that command from its history (which survives a reopen), so a second run, a different command, and a nested call (`call.parent`) are denied; a retry attempt gets no approval. The ticket is identified by the conversation (`api.conversationId`); only the ticket's own rerun creates a conversation with the document, so another ticket never gets it, and the guard fails closed when anything cannot be read. Nothing else is lifted: delivery blocks, never-allowed commands (`rm -rf /`), the commit gate, the branch rule, and the file rules all still apply.

**Pause and resume.** The loop no longer ends `paused`: it sleeps, with no deadline, on `brigadev.resume` key `resume-<n>`, and `status` shows `paused: <reason>`. Reasons: `two consecutive tickets failed: T1, T2`; `doc edited: T#` (S8: a user edit to a runner-owned line; nothing is overwritten); `paused by user` (`brigadev-runner pause`, a `brigadev.pause` signal `pause-<n>` that is read at the next `pick`, so the running ticket finishes first; the pause is not offered to a sleeping loop, which has nothing to pause). `resume` delivers the signal: after a conflict pause the doc is re-read by the phase that found the conflict, and if it is still there the loop pauses again (restore the runner's line, then `resume` again); after the failure pause the consecutive-failure count is reset. `n` is the loop's pause counter, so every pause and resume key is new.

## The PR loop (S2b, S3, S4)

`start` ends the ticket loop with the PR loop unless `--no-pr` is given (the loop task's own default is off, so a loop started through the API with `pr` unset ends `done` as before). It runs when no ticket is left to run: every ticket done or dropped and nothing parked on a decision. `start` is idempotent per doc, and the `--no-pr` choice is the one the loop was first started with: starting it again with the other choice (or from another worktree) is refused, exit 1, with how it was started.

The PR loop is one child task, `brigadev.pr-loop`, launched in one commit that also records its id (a crash never launches a second). **Every git and GitHub action is deterministic runner code through an injectable seam (`PrDeps` in `src/pr.ts`), never a worker tool**: the worker's guard still blocks push, merge, and `gh pr`/`gh release` (a test checks that a fix worker's `git push` is blocked). Phases:

1. **final-check**: the full suite (`resolveCommand`, as the `check` tool does), recorded as evidence by agent `runner`. A failure goes to fix.
2. **verify**: the tier is `branchRisk` over the risk map; only **T2** (or a tier that cannot be known: no base branch) runs `brigadev-verify`. T0/T1 skip it. The verify conversation is owned by the PR loop, with the prompt of `assets/agents/brigadev-verify.md` and the tools `read`, `bash`, and `verify_verdict`. It ends through that terminating tool (the same pattern as `ask_user_choice`: the tool records the verdict in a conversation document and returns `control: { terminate: true }`; the shape is `assets/agents/brigadev-verify.schema.json`, checked with `lib/structured-output.ts`), not by parsing text. Blockers become one fix ticket per verify round with the blockers (each with its reproduction) as its spec, then verify runs again. A run that ends with no verdict, or that leaves the worktree changed (HEAD or files), stops for a person.
3. **push**: `git -c core.hooksPath=/dev/null push --no-verify -u origin HEAD:<branch>`, never forced, no hook of the repository (its config is the agent's to edit), skipped when `git ls-remote origin` already shows that sha, so a crash never pushes a commit twice.
4. **open**: the branch's PR is looked up first (`lookupPr`); `gh pr create --base <default branch> --head <branch> --title <t> --body-file <tmp>` only when there is none, so a crash between create and the checkpoint finds the PR again. The title is conventional: the branch type (`feat/x` → `feat:`; an unknown prefix is `chore:`) and the doc's first heading, else the Objective's first sentence. The body has the objective, the tickets with their commits, the risk tier line, and `Opened by brigadev-runner.` A branch with no commits ahead of its base stops with needs-you instead. A **merged** PR found for the branch ends the loop `merged` only when its head is the commit pushed now; an older merged PR of a reused branch name stops with `an older PR #n for this branch is merged; open a new branch`.
5. **wait-ci**: the task sleeps until now + 60 s (`POLL_MS`, the Harness clock), then reads `gh pr view <n> --json headRefOid,statusCheckRollup,state,isDraft`. Results for a head other than the pushed sha are ignored; pending sleeps again; no checks reported counts as green; a wait lasts at most 24 h, then needs-you. A failure fetches the filtered log (`gh run view <id> --log-failed`, its tail) and goes to fix. A CI wait is a timer of the `start` process: `start` stays in the foreground for it, and parks (exit 1) only when a person is needed.
6. **fix**: the existing `brigadev.ticket` task with a synthetic ticket `FIX-1`, `FIX-2`, ... The brief's `## Spec` carries the failure tail (or the blockers) and "reproduce it with a failing test first (RED), then fix it, run the suite (GREEN), and commit"; `done` is the suite command. One worker attempt per fix, and **3 fix attempts per PR loop**, shared by final-check, verify, and CI. A passing fix goes to push → wait-ci (for CI) or to verify (for final-check and verify). A fix ticket's decision parks exactly like a ticket's (`status` shows it; `brigadev-runner answer <doc> FIX-1 ...`; 24 h; no attempt is used).
7. **wait-merge**: when CI is green, one PR comment `Ready to merge: run \`brigadev-runner merge <doc>\``, then the task parks on the `brigadev.merge` signal, key `merge-<n>`, deadline 24 h. The runner **never merges without it**. On delivery it re-reads the PR and merges only if the PR is open, not a draft, its head is the pushed sha, and no check is failing or pending; otherwise it goes back to wait-ci (and asks for a new approval, key `merge-<n+1>`, with a new comment). Merge is `gh pr merge <n> --merge --match-head-commit <pushed sha>` (never `--admin`, `--auto`, or `--delete-branch`), after the re-read; GitHub refuses it if the head moved in between, which stops for you, so a crash after the merge finds the PR merged and does not merge again. An approval not given within 24 h stops with `merge approval expired`.

A PR merged by someone else ends the loop `merged` too. The loop's result is `{ status: "merged", url, number, tickets }`; `pr-failed` if the PR loop task itself failed or was aborted.

**Needs you.** Any stop in the PR loop (3 fix attempts used, an expired approval or CI wait, a refused push, a closed PR, a verify without a verdict, no commits to open a PR for, ...) posts **one PR comment** (`gh pr comment <n> --body-file`, once per stop; skipped when no PR exists yet), appends one `## Log` line through the doc's atomic write, and parks on `brigadev.resume` (key `resume-<n>`, no deadline). `status` shows `pr: needs-you` with the reason; `brigadev-runner resume <doc>` continues at the phase that stopped with a fresh fix budget.

**What the runner does on GitHub**: `gh pr view`, `gh pr create`, `gh pr comment` (the ready-to-merge and the needs-you comments), `gh run view --log-failed`, `gh pr merge <n> --merge --match-head-commit <sha>`, and `git push -u origin HEAD:<branch>`. Nothing else: no force push, no delete branch, no release, no admin or auto merge.

**Persistence (S3).** Each phase is safe to rerun: the suite and the reads repeat; the push asks the remote first; the PR is looked up before it is created; the fix budget is charged in the commit that creates the fix ticket (the fix ticket's own conversation is found again by position); a merge re-reads the PR first. A comment is memoized *before* it is posted, so a crash between the two can lose a comment but never duplicates it (`status` still shows the command). `tests/pr-persistence.test.ts` kills the runner at final-check, push, open (between create and the checkpoint), wait-ci, fix, and wait-merge (also right after `gh pr merge`, and with the approval expired meanwhile), on JSONL and SQLite.

`status` shows the PR phase (`final-check`, `verify`, `push`, `open`, `wait-ci`, `fix <n>`, `wait-merge`, `needs-you`), the PR url, the `merge:` / `resume:` command while the PR loop waits for one, and a `warning:` line when the last PR comment could not be posted (the Log line says `PR #n comment failed: <stderr>`; the loop goes on).

**What the runner publishes is redacted** (`src/redact.ts`): every PR comment, `## Log` line, and ticket note has credentials in URLs (`https://user:tok@host` becomes `https://***@host`), token-looking strings (`ghp_…`, `github_pat_…`, `sk-ant-…`, 32 or more hex or base64 characters), and the home directory (`~`) removed, because they quote git and gh stderr, suite output, and the local doc path.

Not in the PR loop yet: cost caps (the L8 limits).

## The board (S6)

`start <feature-doc> --web [--port N]` serves the existing brigadev web UI (`lib/web-server.ts`, `lib/web-page.ts`, `assets/web-ui/`) from the runner process, on `127.0.0.1` only (port: `--port`, else `BRIGADEV_WEB_PORT`, else any free port). The board starts before the loop is scheduled and prints a **one-time link** to the runner's terminal (`brigadev board: http://127.0.0.1:<port>/?code=… (one-time link, valid 60 s; press Enter in this terminal for a new one)`). Open it in a browser you trust. Without `--web` nothing changes.

**Where `--web` runs.** Only in a plain interactive terminal, so that nothing a worker can read holds the link:

- **A terminal on both ends (H2).** `--web` requires stdin and stdout to be terminals; otherwise it exits 2 with a message before anything starts (no store, no lock, no server). The link is written only to that terminal, and a fresh one only on **Enter** there. A pipe, a file, or a service's log can be read by other processes of yours, the worker's bash included.
- **No signal asks for a link (H1).** `kill -USR1 <pid>` does nothing (the runner still holds a SIGUSR1 listener, only to keep Node's inspector closed). Any process of yours can send a signal; only someone at the runner's terminal can press Enter.
- **Not inside tmux, screen or zellij (H3).** With `TMUX`, `STY` or `ZELLIJ` set, `--web` exits 2 and says why: a pane can be read (`tmux capture-pane`) and typed into (`tmux send-keys`) by any process of your user, the worker's bash included, and the link and the Enter are on that pane. `--web-in-multiplexer` overrides the refusal and prints a warning; use it only when nothing untrusted runs as you.
- **In the foreground of that terminal (R4-003).** `start … --web &` (or a job sent to the background later) is refused with exit 2 before anything starts: reading the terminal from a background job raises SIGTTIN, which stops the process, and the runner would sit suspended mid-loop holding the store. Node has no `tcgetpgrp`, so the check reads the process's group and the terminal's foreground group once at start-up (`/proc/<pid>/stat` on Linux, `ps -o pgid=,tpgid=` elsewhere); when neither can be read it does not refuse. Run it in the foreground (`fg` brings it back). Ctrl-Z followed by `bg` is the shell's own job control: the runner stops at its next read of the terminal until `fg`.
- **The worker has no terminal (H4).** Every bash call of a worker, verifier or fix conversation runs in its own session and process group (no controlling terminal, so it cannot write to or inject keystrokes into the runner's terminal as its own), with stdin on `/dev/null`, and the whole group is killed when the call returns (SIGTERM, then SIGKILL after 1 s for what ignored it; a pending SIGKILL is also sent at once when the environment is cleaned up and when the runner exits, so a SIGTERM-ignoring script started by the last call does not outlive the runner), however it ended. A `nohup … &` script does not outlive its call. The runner checks at start-up that the installed `pi-durable` still reports each command to the hook this relies on, and refuses to run when it does not. See [Containment](#containment-what-it-stops-and-what-it-cannot) for what escapes.

**What it shows** (`src/board.ts`; the page is in runner mode, which the `session` snapshot's `kind: "runner"` switches on: no composer, the Abort button reads **Pause**, no cancel buttons, the title is `brigadev-runner · <doc>`):

- the ticket list as the Tasks drawer (`brigadev:todo`), the loop phase (implement while a ticket runs, check in final-check, verify, CI and fix, commit for push, open, and the merge wait, close when merged; `decide` while only decisions wait; `idle` when paused or stopped), and one card per ticket that ran or runs: `brigadev-worker`, status `running`, `done`, `failed`, `blocked`, or `needs-you`, the commit, the failure or the park reason, the attempts, and the worker's last tool calls (read from its conversation in the store, newest 60 entries, 8 calls kept), plus `FIX-n` tickets and one `pr` card for the PR loop (phase, PR link, CI state, why it needs you). The CI state is derived from the PR loop's phase: the PR loop keeps no check results in its state, and the merge gate re-reads them anyway. The card statuses `blocked` and `needs-you` are the runner's own words beside the bus's `queued|running|done|failed|cancelled`: the page shows them as text.
- **Needs you** cards (`brigadev:prompt`, open until the state moves on, then answered or dismissed whoever answered; one answered in the browser is shown answered, one answered with the CLI after a restart is shown dismissed because the board does not know the answer): every open ticket decision (a choice with its options, the recommended mark, and free text; its id is the signal key `decision-<T#>-<n>`), the merge approval while the PR loop waits for it (`Merge PR #n at <short sha>?`, the PR link and the CI state; id = the merge key), a paused loop (`Resume the loop?` with the reason) and a PR loop stop (`Resume the PR loop?`).
- Everything is sent through one gate first (`src/board.ts`), which applies both `lib/redact.ts` and `src/redact.ts` (the second also masks standard base64 with `+` and `/`, such as an AWS secret key): reasons, failure output, commands, worker text, and what a refused action says.

**What it can do.** The page's actions go to the live `Runner` of the `start` (the Harness that holds the store lock), through the same functions as the CLI (`src/control.ts`), so the loop wakes in this process and nothing has to run `start` again:

| Page action | Effect |
|---|---|
| answer a decision (an option, or free text) | `answer`: the option's number, or the text; an option whose label starts with `Approve` lifts the denied command for that exact command, once, as with the CLI |
| Approve the merge | `merge`: the runner re-reads the PR and runs `gh pr merge --merge --match-head-commit <sha>` only when it is open, not a draft, at the pushed commit, and green |
| Approve resume | `resume` (the loop's pause, or the PR loop's stop) |
| answer the cost-cap prompt (`+$5`, `+$10`, or an amount in dollars) | `resume --cap`: `+$N` is a cap $N above the spend, an amount is the new cap itself; at or below the spend it is refused with 409 and the prompt stays open |
| Pause (the Abort button) | `pause`: at the loop's next pick; refused while paused or while the PR loop runs, as the CLI does |
| Deny on the merge or resume prompt | nothing: the runner keeps waiting and the prompt stays open |
| message, cancel a card | refused with 409 and a reason: there is no conversation to message, and a ticket is not cancelled (pause instead) |

An answer to a prompt that is not open now (answered elsewhere, or the loop moved on) is refused with 409 and the page says so, as in the Pi web UI; so is anything the CLI would refuse (`duplicate`, `closed`, `invalid`, a pause while paused). An answer acts only on what the page showed (R1-001): the prompt's identity travels with it (the decision's signal key; the merge's key **and** the PR head commit its title names; the resume key), the control checks it against the state it reads itself in the call that delivers, and delivers with that key, so a new decision round, a new push, or a new pause between the page's view and the click is a 409 and nothing is delivered. The board cannot approve anything else: it has no action that reaches the worker, the guard, or the doc.

**The process stays up** while the loop waits for a person (that is how the board's answers reach it; the store lock is held), and exits when the loop ends (completed, failed, aborted) after one last publish and a short linger (so an open page shows the end). On SIGINT or SIGTERM it closes the board and the runner cleanly (a second signal kills it) and exits 1: the loop continues from storage on the next `start`. A fresh link: Enter in the runner's terminal; each prints a new one-time link (never a signal, see above). The page says so when its link was used or expired. A `--port` that is already taken exits 1 with a message that says so; a failed or stalled loop, or a PR loop that failed, ends the start with exit 1 (0 only for done or merged).

**Auth and what it does not stop** are the web UI's, unchanged (it is the same server and page): the link's `code` (32 random bytes, 60 s, single use) is exchanged at `POST /session` for a session secret that lives only in the page's JavaScript and travels as `Authorization: Bearer`; Host and Origin are checked, and a code or secret in a query string is refused. The code is printed only to the runner's terminal: it is not written to the store, the doc, the `## Log`, a PR comment, or stderr (`tests/board-cli.test.ts` checks the doc, the commits, and the outputs), and the worker's contained environment holds nothing of it (it is in no variable or argument). `tests/board-security.test.ts` replays the attack that found the earlier design open: a worker's script (in its call, and as a `nohup` background copy) that signalled the runner with SIGUSR1 to make it print a fresh link, read it from the runner's output, signed in and answered its own decision with `Approve: rm -rf build`. Residual risks, as for the web UI: a process of your own user that reads the code before the page uses it (something scraping the terminal's scrollback or the clipboard, or reading the terminal's device through the operating system's own tools) or that reads the browser's or the runner's memory can sign in and then approve a merge or answer a decision. The worker runs with the contained environment, its guard, and no terminal, but it runs in your account like those processes: see [Containment](#containment-what-it-stops-and-what-it-cannot). A merge approval from the board has the same effect as `brigadev-runner merge`, so open the link only in a browser you trust, and prefer a container or a VM account for unattended runs.

## The worker obeys the guard

S5: the worker follows the same rules as the brigadev extension, decided by the Pi-free modules in `../lib/` (`guard-rules.ts`, `command-classifier.ts`, `permission-policy.ts`, `commit-branch.ts`, `evidence.ts`, `check.ts`, `repo-docs.ts`, `runtime.ts`), not copies of them.

- **One hook** (`src/guard.ts`): a `beforeTool` hook on pi-durable's `ToolTask`, selected by every worker conversation. It decides each call, including nested calls (`call.parent`, as a code mode script makes). A call it cannot decide is blocked (a throwing hook blocks in pi-durable too).
- **File tools** (`read`, `write`, `edit`) go through `decideFileAccess` with the worktree as the project root, as for an extension subagent: nothing is written outside the worktree, secret-looking files are blocked, and the evidence log is blocked. Also blocked for writes: git config and hooks (`isProtectedPath`) and anything in the repo's harness documents folder (the feature document is the runner's to write).
- **bash** goes through `decideBashCommand` with the permission mode from `~/.pi/agent/brigadev.json` (`defaultMode`, default normal), the evidence-write rule (`bashWritesEvidence`), and the branch rule: a commit is allowed only on a feature branch, in every mode.
- **Nothing asks.** A `confirm` result (`rm -rf`, `git reset --hard`, an install, `sudo`, a commit off a feature branch, ...) is denied with `needs you: <reason>` (Q6). The worker is told not to retry it, and, for a bash command, how to get it approved: a decision with `command` set (see [Decisions, approvals, pause and resume](#decisions-approvals-pause-and-resume-s4-s9)).
- **A commit stands alone**: a bash call that commits may hold only `cd` and `git add`/`status`/`diff`/`log`/`show`/`rev-parse`/`commit`, with no output redirection. The gate reads the working tree before the command runs, so a write in the same call would be committed untested.
- **The runner owns delivery**, whatever the mode: `git push` (also forced), `git pull`, `git merge`, `npm publish` and the other publish commands, `gh pr ...`, `gh release ...`, and `gh api` writes are blocked with `the runner owns PR delivery`.
- **Unknown tools are blocked.** The worker has `read`, `write`, `edit`, `bash`, `check`, and `ask_user_choice`.
- **The verifier is read-only.** The PR loop's verify conversation is marked by a `brigadev.role` document and decided by a read-only guard (`readOnly: true`): its tools are `read`, `bash`, and `verify_verdict`; `write`/`edit` do not exist for it; bash may not commit, may run only read-only git subcommands (`status`, `diff`, `log`, `show`, `rev-parse`, ...), and may not write a file inside the worktree by a literal name (redirections, `tee`, `cp`, ...). Beyond that, `git diff --output`, `--ext-diff`, `--textconv`, and an interpreter with inline code (`python -c`, `node -e`/`--eval`/`-p`, `perl -e`/`-pi`, `ruby -e`) are blocked, and `sh script`/`bash <<EOF` (an opaque shell) is too. Like the extension's rules for bash this is best effort (a node script file can still write), so the PR loop also compares before and after the run, and stops for a person if anything changed: the worktree's content as a full tree hash (so an edit to a file that was already dirty is seen, which HEAD and `git status` cannot show) and the integrity snapshot below. A role that cannot be read fails closed (both rule sets apply).
- **Commit gate**: a `git commit` is allowed only when `evaluateCommitGate` allows it for the current tree, against the same evidence file the extension reads (`<docs>/evidence/<branch>.jsonl`): a passing test run on this exact tree (or a docs-only change). A blocked commit returns the gate's reason to the worker. The worker cannot force it.
- **`check` tool** (`src/check-tool.ts`): the extension's `check` over `lib/check.ts`: same parameters (`command`, `focus`, `timeoutSeconds`), the command from `check.test` in `brigadev.json` or detection, the same refusal of commits, pushes, and publishing, a compact `PASS`/`FAIL` result, and the run is appended to the evidence file with agent `runner-worker`. The worker's instructions say to run `check` before committing and to make no edit between `check` and `git commit`. Tests run through `bash` are not recorded. The suite runs with the contained environment and the pinned settings (below); `check.test` is read when the runner opens, never again, so a worker that rewrites `brigadev.json` changes nothing.

- **The string layer for credentials** (`src/containment-rules.ts`, worker and verifier alike; best effort, see below): `git -c`/`--config-env`/`--exec-path` and `git config` writes (`<key> <value>`, `--add`, `--unset`, `--global`, `--file`, `alias.*`; reading a key is fine), git plumbing that writes refs or remotes (`update-ref`, `send-pack`, `http-push`, `commit-tree`, `fast-import`, a writing `symbolic-ref`, `remote add|set-url|…`, `branch -f|-M|-D`, `checkout -B`, `fetch` with a refspec), `git credential*`; `gh api` with a method other than GET in any spelling (`-X`, `-XPUT`, `--method=…`), a body (`--input`, `-f`, `-F`, `--field`, `--raw-field`), or `graphql`; `gh alias|extension|auth|ssh-key|gpg-key|secret|variable`; setting, unsetting, or exporting a credential or containment variable (`GH_CONFIG_DIR`, `GH_TOKEN`, `GITHUB_TOKEN`, `GIT_SSH`, `GIT_SSH_COMMAND`, `GIT_CONFIG*`, `GIT_ASKPASS`, `SSH_AUTH_SOCK`, `SSH_ASKPASS`, `HOME`, …), inline, with `env`, `export`, or `unset`; credential stores by name (`security`, `credential-osxkeychain`, `.git-credentials`, `.netrc`, `.config/gh`, `hosts.yml`); and a shell that reads its program from a heredoc, here-string, or pipe. **This layer is best effort**: it reads commands, not scripts. `gh pr view` stays a delivery block (the runner owns `gh pr`).

Differences from the extension's subagent rules, on purpose: the worker must commit (bash is decided like the parent's, files like a child's), the commit gate applies to it, the branch rule holds in yolo too, there is no one to confirm so confirmations are denials, and delivery is always blocked.

## Containment: what it stops and what it cannot

The worker and the verifier run bash in the user's account, with the user's credentials within reach. A string guard cannot contain that: the agent can write a script the guard cannot read and run it later. So containment is layered, strongest first:

1. **The environment (the barrier).** Every process that runs worker-authored code or worker commands gets `containedEnv` (`src/contain.ts`): the worker and verifier conversations' bash, the ticket's `done` command, the `check` tool's suite, and the PR loop's final-check suite. It has no `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `SSH_AUTH_SOCK`, `SSH_AGENT_PID`, `ANTHROPIC_API_KEY`, nor any variable whose name contains `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `API_KEY`, `APIKEY`, `CREDENTIAL`, or `PRIVATE_KEY`. `GH_CONFIG_DIR` is an empty directory in a scratch directory made per runner process and removed when it closes (`gh` is logged out); `GH_PROMPT_DISABLED=1`, `GIT_TERMINAL_PROMPT=0`, `GIT_ASKPASS` and `SSH_ASKPASS` are `/usr/bin/false`, `GCM_INTERACTIVE=never`, `GIT_CONFIG_NOSYSTEM=1`; `GIT_SSH_COMMAND` is `ssh -o BatchMode=yes -o IdentitiesOnly=yes -o IdentityFile=/dev/null -o IdentityAgent=none`; and `GIT_CONFIG_COUNT` entries reset the credential helper list (`credential.helper=`), and set `core.hooksPath=/dev/null` and `core.fsmonitor=false`, which override whatever the repository's config says. `HOME` and `GIT_CONFIG_GLOBAL` are kept, so `user.name` and `user.email` work. Only the PR loop's own `git push`, `git ls-remote`, and `gh pr *` calls keep the real environment. (`lib/check.ts` spawns with `process.env` and is not editable from here, so `src/check-run.ts` is a copy of its `runCheck` with the environment as a parameter; keep them in step.) At the CLI script's entry the runner process's own environment gets the hook and fsmonitor entries too, so the guard's and the commit gate's git calls run no program from a config the agent edited.
2. **The string layer (first layer, best effort).** The guard blocks the obvious routes with a reason the agent can read: see [The worker obeys the guard](#the-worker-obeys-the-guard). It reads commands, not scripts: `sh x.sh` and `node x.js` pass, and a heredoc-fed shell, `sh script` for the verifier, and inline interpreter code are blocked only because they are opaque.
3. **The integrity check (detective).** Around every worker conversation (each ticket attempt, each `FIX-n`) and the verify conversation the runner snapshots (`src/integrity.ts`): a hash of the feature document; of `<agent dir>/brigadev.json`; of git's config (the common dir's `config`, `config.worktree`, the global files) and of every file in `<common dir>/hooks`; every `refs/heads/*` and `refs/tags/*` and where HEAD points; and the remote's refs (`git ls-remote origin` with the real environment; skipped when there is no `origin`, when it cannot be read, or when the config changed, so a changed config never points the runner's own `ls-remote` at a program of the agent's). The snapshot runs no hook and no fsmonitor program (`-c core.hooksPath=/dev/null -c core.fsmonitor=false`, files read with fs). After the conversation, **before the ticket's done check or the verdict is trusted**, the two are compared. The only change allowed is the feature branch moving (its commit, with HEAD staying on it; for the verifier not even that). Anything else parks the loop with the list: the ticket loop pauses (`the worker changed brigadev.json, refs/heads/main, origin refs/heads/x; check them, then resume`, one Log line, the ticket stays `in_progress`), the PR loop stops needs-you (a comment, a Log line, `resume`). `resume` accepts the state: the ticket runs again from the commit it started at with a fresh snapshot; after a fix worker's stop the PR loop starts again at the final check.
4. **Pinned settings.** `brigadev.json` is read once when the runner opens and passed to the guard, the `check` tool, and the PR loop; nothing rereads it, so a worker that rewrites `check.test` or `defaultMode` changes nothing (and is reported by the integrity check).

**What this cannot stop.** Be clear about it before running unattended on a machine that holds credentials:

- **Credentials on disk.** A script can read an unencrypted private key (`~/.ssh/id_*`; `IdentityFile=/dev/null` and `IdentitiesOnly` only keep `ssh` from using the default keys itself, a script can use the file with its own `ssh -i`), a token in a dotfile (`~/.npmrc`, `~/.aws/credentials`, a `.env` outside the worktree), the Pi agent's own `auth.json`, or the keychain through an API instead of the `security` command. The guard blocks credential stores by name only. The environment barrier removes what the *environment and the usual helpers* hand out; it does not remove what a process running as the user can read.
- **The network.** There is no network sandbox: anything the agent can read it can send anywhere.
- **Everything else the user's account can do locally.** Bash is not confined to the worktree (only the file tools are); the agent can write any file the user can, including shell rc files and files outside the snapshot.
- **Anything after the fact.** The integrity check is detective: a push, a ref change, or a planted hook has already happened when it is reported. The runner parks and says what changed; it does not undo. Only `origin`'s refs are read, and only the listed state is compared.
- **A user's edit during a worker run.** Any change of the feature document during a worker's conversation parks the loop, yours included.
- **Forged evidence.** A script can write the evidence log: the commit gate is quality control, not a security boundary.
- **A process that makes its own session or group.** A bash call's processes are killed with the call's process group (H4), but a process that creates a new session or group of its own (`setsid sh x.sh &`, a script that calls `setsid()` or `setpgid()`/`setpgrp()`, a daemonizing program, `at`/`cron`/`launchd`) is no longer in that group and outlives the call. The same goes for a runner that is itself killed by a signal or crashes (no `exit` event, so no pending SIGKILL is sent). It still has no terminal and no way to signal the runner into printing a link (no signal does), but it keeps running as you, with the same reach as anything else on the "Everything else the user's account can do locally" line. The `done` command and the `check` suite are also run in their own group, killed only on a timeout or an abort, not when they return.
- **The link on the clipboard, and terminals that can be read back.** The link is safe on the runner's terminal only until you copy it: any process of yours can read the clipboard (`pbpaste`, `xclip`) and race the page to the one-time code, so open the link by clicking it, not by copying. Terminals with a scripting or remote-control API give any process of yours the screen text too (iTerm2 and Terminal.app AppleScript, `wezterm cli get-text`, `kitty @ get-text`); `--web` refuses only tmux, screen and zellij, so use a terminal without one for `--web` or a separate account.
- **Text written to the runner's terminal.** A process of yours can open the terminal device for writing (`/dev/ttys*`, `/dev/pts/*`) and print text on it, a fake `brigadev board:` line with a link to its own listener (phishing). It cannot type into the terminal (`TIOCSTI` is refused) or read it. Open only the link the runner printed, in the runner's own window.
- **Other Node processes of yours.** SIGUSR1 opens Node's unauthenticated inspector in any Node process without a listener for it. The runner holds one, and `npm start` passes `--disable-sigusr1`, but `npm` itself is a Node process with the runner's environment: start the runner with `node --disable-sigusr1 <path-to>/runner/src/cli.ts start …`, not through npm. The agent can still signal your other Node processes (MCP servers, editors, a Pi started through `npx`).

For a guarantee run the runner where there is nothing to steal: a container or VM, or an OS account with no credentials, with `gh` and git configured for the runner only. That is the recommended way to run it unattended.

## Tests

```sh
cd runner
node --test tests/*.test.ts      # or: npm test
```

The board tests (`tests/board.test.ts`, `tests/board-cli.test.ts`) run the adapter and the actions end to end over HTTP on an ephemeral 127.0.0.1 port, with a session secret from the one-time code, against the same fixtures; the page variant is checked by `../tests/web-runner-page.test.ts`. `tests/board-hardening.test.ts` runs the board over a scripted `Runner` (redaction, an answer acting only on what the page showed, the refresh coalescer, `stop()` mid-read); `tests/board-security.test.ts` is the verify's attack as a regression test; `tests/reaping-env.test.ts` and `tests/bash-reap.test.ts` cover the worker's bash calls ending with their process group; `tests/ticket-runs.test.ts` counts what `ticketRuns` reads from a store that holds another loop.

Tests use pi-ai's scripted faux provider and a temp git repo on a feature branch; no network, no model. The guard, the evidence log, and `brigadev.json` read the environment, so the tests point `BRIGADEV_HOME` and `PI_CODING_AGENT_DIR` at a temp dir (`isolateEnv()` in `tests/fixture.ts`): the real `~/.brigadev` is never written. They take minutes where `git` is slow to spawn, because every scripted commit runs the commit gate (several git calls) on top of a real `git commit`. The persistence tests close the Harness while ticket 1's done command is running (after the worker answered), reopen the same JSONL / SQLite storage, and check ticket 1 is not run again. `tests/decisions.test.ts` parks a decision, closes, reopens (JSONL and SQLite), delivers the answer without scheduling, and resumes; it drives deadlines with the manual clock `fakeClock()` (the Harness `now`/`setTimer` options). `tests/pause.test.ts` and `tests/control.test.ts` cover pause/resume and the CLI commands. `tests/cost-cap.test.ts` covers the cost cap: the faux provider reports no cost, so `makeWorker(scripts, { price })` wraps it (`priced()` in `tests/fixture.ts`) to report `price` dollars per response, which makes N responses exactly N × price. A user's "meanwhile" edit of the doc is made through `depsWithHook` (while a done command runs, after the worker's conversation), because a doc change during a conversation is an integrity finding. `tests/contain.test.ts` (the environment of each process that runs the agent's code), the containment table at the end of `tests/guard.test.ts`, `tests/integrity.test.ts` (the snapshot, and the loops parking on a worker's or verifier's doc, settings, hook, ref, remote, and worktree changes), `tests/lock.test.ts` (ten processes racing for a lock left by a dead one, three rounds), and `tests/hardening.test.ts` (redaction, the done timeout, an older merged PR, a failing comment) cover the containment and the warnings. A worker's commit in a test is a plain `git commit` (the guard blocks `git -c`); the identity comes from `GIT_AUTHOR_*`/`GIT_COMMITTER_*` set by `isolateEnv()`.

The PR loop tests (`tests/pr-loop.test.ts`, `pr-persistence.test.ts`, `pr-cli.test.ts`) use a real local bare git remote (`<tmp>/remote.git` as `origin`, real `git push`) and a fake `gh` (`tests/pr-fixture.ts`) that keeps its own PRs, comments, checks, and merges; only `gh` is faked. CI polls are driven with the manual clock (`clock.advance(POLL_MS)`), and a kill is `runner.close()` while an outside call hangs, then a reopen of the same storage with the same clock.
